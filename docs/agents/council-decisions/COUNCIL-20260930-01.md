## Proposed immutable recommendation v1

Outcome/ownership: Stage 1 SCKRL-312 adds optional durable receipt expiry entry and an enabled saved-review exit with recovery. Frontend owns the ticket, Backend owns schema/command/client prerequisites, Infrastructure reviews an ADR-0001 addendum, and separate QA remains the acceptance gate. Ratification makes the implementation contract Ready; it does not close 304/406/312, apply/replay migrations, deploy, commit or merge. SCKRL-311 follows this contract; SCKRL-305 follows 311. Media/OCR, notification delivery, prediction providers and full receipt history remain separate tickets.

Receipt expiry: persist exactly unknown, dated, no_date. unknown means no date entered; dated carries one valid Gregorian YYYY-MM-DD date; no_date means the user chose 'Leave without a date', without claiming anything about package labels. 'Remove entered date' returns to unknown; there is no fourth cleared state. Backfill and new parser/manual lines default unknown with null date and attribution. Dated input uses source:user only; purchase date and parser confidence never supply expiry evidence or printed source.

Save/compatibility: expiry is an optional strict state/date object within the full SCKRL-310 generation/revision-guarded review save. Omission preserves existing expiry and defaults new lines to unknown, so old clients cannot erase saved expiry. Explicit unknown resets a saved value; explicit no_date records the intentional app choice. Invalid combinations, dates or client-supplied actors/times are rejected atomically. Database-owned expiry_changed_by/at change only on actual state/date mutation (including reset), survive unrelated edits and unchanged saves, and are distinct from row reviewed_by. Normalized expiry participates in correction/review equality: editing expiry on an included row requires explicit review again; choosing an optional unknown/no_date state is valid and never creates a missing-date blocker. Excluded lines may retain saved receipt choices but create no stock, expiry facts or acquisition events. Review conflict/failure never silently replaces the local draft or writes over the newer generation.

Stock conversion: initial 311 reads locked persisted expiry; the client does not copy dates/provenance into placement. unknown becomes expires_on:null with no fact. dated becomes a declared user fact with unknown printed marking, null confidence/version and confirm:false. no_date becomes a declared user fact with expires_on:null, unknown marking and confirm:false. Receipt-specific reviewer attribution remains on the source line; 406 records the placing actor as writer and grants no inherited confirmation. Initial placement has no expiry-confirmation flag/control. The existing stock confirmation flow may later confirm a dated fact as the acting user; an explicit placing-user affirmation is a deferred alternative requiring its own accepted UI/payload refinement.

Estimation choice: unknown receipt dates receive no automatic estimate in this increment. This consciously narrows the Phase 2 expectation that placement starts 405 and requires an explicit receipt-flow exception in canonical 405 documentation. Existing stock Add/Edit estimation stays under its accepted contract. A later receipt-estimation refinement must decide a trustworthy purchase/base calendar day, category/zone/version policy, preview consistency and confirmation; neither parsed purchased_on nor placement-day reset is silently adopted here.

311 transition/recovery: inputs identify household, receipt, generation, expected review revision, stable idempotency key and the exact included-line-to-household-zone assignments. The server checks current authenticated membership, locks the receipt and necessary referenced state, validates the saved reviewed line set and zones, then atomically commits stock, unique source-line lineage, facts where applicable, acquisition events and an immutable placement record/result. Same key plus identical normalized input returns the original result before stale-token checks; the same key with different input conflicts. A second key cannot place an already placed receipt and returns a clear already-placed conflict with an authenticated canonical status/result read. Timeout recovery retains key, immutable input and local draft, reads canonical receipt/key status, and may retry the identical operation with the same key; an unplaced GET is not proof no command remains in flight. No success/stock claim is shown from an uncertain response. Membership is checked before cached replay. After committed placement, saves and parse-promotion/failure commands reject under the same receipt lock; the initial review is read-only. This explicitly defers canonical 306 post-placement re-edit until a separate correction contract defines source snapshot/stock lineage semantics.

Calendar/UX: calendar dates retain their year/month/day across locale, device timezone, household timezone and DST; locale controls display, never timestamp conversion of the stored value. Validate real dates, including leap days; allow past dates with clear ordinary date display. Provide accessible unknown/date/no_date choices, a labelled optional date control, readable state labels and tap/screen-reader paths. A clean saved review offers 'Done for now' to the deterministic Home route with 'Review saved. Items are not in stock yet.' Home provides a bounded authenticated pending-review entry that reopens that same receipt ID after restart; durable resume ships with the exit, without implementing full receipt history. Account/household scoping and authoritative status checks prevent stale or another account's entry. Unsaved, failed, conflicted or uncertain saves do not claim safe saved exit: preserve drafts and offer keep editing, save/reconcile or explicit discard before leaving. All-excluded reviews may save and exit but cannot place zero stock. Placement validation failures preserve recoverable state and identify the field; stale review requires reconcile/review, already-placed status opens the committed result, and only confirmed transaction success reports items added to stock. Copy never claims reminder scheduling without a committed reminder capability.

Evidence/gates: source evidence is the accepted 310/406 contracts and commands, 406's auth.uid()-owned fact attribution, current API listReceipts and current absence of a Home receipt entry, plus the owner's editor/save findings. Before implementation, record persistence/attribution/freeze/idempotency in ADR-0001 and update affected feature contracts. Separate QA must cover legacy/old-client omission, parser/manual rows, invalid shapes/dates, clear/no_date differences, attribution and two-member placement, unchanged metadata, expiry review reset, excluded/all-excluded rows, stale generation/revision, cross-household access, races, rollback, same/different-key retries and lost responses, placed immutability, reload/restart resume, account changes, locale/TZ/DST, modal/keyboard/accessibility and honest success copy. Required migration replay and connected/native checks remain pending under existing authorization restrictions; design votes and source tests cannot substitute for them.

Alternatives/strongest counterargument: immediate estimates and inherited review confirmation would produce more dated/confirmed stock and better recipe coverage with fewer user actions; snapshot-plus-post-placement editable review would preserve 306's original re-edit aspiration. They expand unresolved estimator, actor-attribution or lineage semantics. The bounded initial contract accepts sparse unknown-date stock and an additional later stock confirmation action in exchange for truthful provenance and stable recovery. Unknown-date stock remains subject to 506's existing recipe eligibility rules; no safety inference is added.

## Chair review

The Chair accepts Product and QA's v1 objection: the wording must distinguish an unknown or skipped date from an intentional no-date record. V2 changes only that control label and its helper/accessibility copy; the persistence and placement contract is unchanged. All v1 participants must vote afresh on the full v2 text below.
