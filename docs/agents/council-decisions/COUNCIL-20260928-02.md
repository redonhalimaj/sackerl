## Recommendation

Implement a bounded SCKRL-304 receipt review slice next:

> Build the mobile receipt review route for an existing active parse generation, with editable
> rows, explicit review, manual-line support when a generation exists, save/retry behavior, and an
> honest placement boundary. Move SCKRL-304 to Review only after implementation, focused validation,
> independent QA source review and Chair integration review; do not mark it Done until the remaining
> connected/runtime/visual evidence is complete.

This is implementation work, not merely planning. It uses the accepted SCKRL-310 contract already
present in `packages/api-client/src/receipts.ts` and keeps storage, OCR and placement out of scope.

- `features.md` defines SCKRL-304 as `ScreenReview` with top confidence chips, editable name,
  quantity, unit and category, add-missing-item support and no continuation while lines need review.
- `docs/features/sckrl-310-receipt-review-data.md` establishes the stable review snapshot and save
  contract. Parser confidence is immutable evidence; `reviewState` and `included` control review
  completion. `saveReceiptReview` needs an active generation, expected review revision and a full
  line list. The SCKRL-310 migration must not be applied or replayed by this task.
- `packages/api-client/src/receipts.ts` exposes `getReceiptReview` and `saveReceiptReview`; the
  summary `canComplete` means no unresolved fields and at least one line. It does not require
  `includedCount > 0`, so the mobile UI must separately avoid claiming there are items to place
  when all lines are ignored.
- `apps/web/app/receipts/[id]/items/route.ts` already wraps the same review read/save contract for
  web callers.
- `apps/mobile/app/(tabs)/scan.tsx` currently creates an uploaded receipt row with a synthetic
  `sackerl://receipt/...` reference and only displays the ID. It does not parse, navigate to review,
  upload real media or start OCR.
- No mobile receipt review or placement route exists today.
- ADR-0001 says confidence is not review approval, failed reprocessing must preserve the previous
  good generation, and SCKRL-311 owns atomic placement and stock writes.

Phase 2's older confidence language must yield to the accepted SCKRL-310/ADR contract: high
confidence can help the user scan the list, but it cannot auto-approve a line. Any batch action
must be an explicit user action that changes draft review state.

Frontend independently reviewed v1 before the roster correction and supported the same SCKRL-304
scope with emphasis on these boundaries: "Save review" is the real action; placement remains
disabled and explanatory; stale 409-like conflicts preserve the visible draft and offer reload;
manual additions require a generation and stable client IDs; all-ignored reviews can save but cannot
place. Because v1 had obsolete participants, this is carried as source evidence only and is not
counted as a v2 vote until reconfirmed.

## Alternatives considered

### Close SCKRL-406 evidence now

Not selected. SCKRL-406's remaining acceptance evidence is exactly the evidence the current
restriction blocks: corrected SQL replay, migration/fixture validation and authenticated
PostgREST/native flow checks. More source reading can clarify the situation, but it would not
complete the next program step. Hosted migration state is unknown and must not be inferred.

### Start SCKRL-308 private media storage

Not selected for this work item. SCKRL-308 is strategically important and unblocks real
acquisition, but the implementation crosses storage policy, private bucket configuration, upload
authorization, retention and cleanup. Under the no-migration/no-deploy/runtime-change restriction,
it would collapse into another contract-only exercise or unverifiable external setup. It should be
scheduled when Infrastructure can participate and Supabase storage changes are authorized.

### Advance SCKRL-908 mobile smoke coverage

Not selected as the next concrete product step. SCKRL-908 remains useful, but full mobile smoke
coverage depends on a development build, isolated fixtures and existing surfaces. It should add
coverage after the SCKRL-304 surface exists rather than substitute for the missing receipt review
implementation.

### Implement SCKRL-304 receipt review

Selected. SCKRL-304 has accepted prerequisites locally, a stable SCKRL-310 typed contract, clear
mobile source seams and no need for new schema, storage or provider selection. It makes the receipt
loop visibly more real while preserving honest runtime gates.

## Proposed implementation scope

If ratified, implement this bounded slice. Under v3, "implementation owner" means root/Chair taking
over the saved partial route/helper source and completing tests after the Frontend writer stopped.

- The implementation owner owns a mobile route for receipt review, expected path
  `apps/mobile/app/receipt-review/[id].tsx`.
- The implementation owner owns a focused draft/helper module for review mapping, validation and
  save-payload construction.
- The implementation owner owns focused tests for the helper and the route behavior using mocked
  auth/profile/receipt clients.
- Root may wire Scan entry/navigation after receipt creation and app layout only if needed so the
  created receipt ID can open the review route. If the receipt has no active generation, the route
  must show an honest processing or unavailable-review state with refresh and manual grocery
  fallback; it must not invent a parse generation, promote deterministic parser output or start OCR.
- Display the ScreenReview-compatible surface where SCKRL-310 data exists: receipt header, sage
  confident chip, amber needs-review chip, raw text under parser rows, and editable row fields.
- Treat every included line as needing explicit user review until its `reviewState` is `reviewed`.
  Confidence is display metadata only.
- Support editing name, quantity value, unit and category; excluding/including a line; marking a
  line reviewed; and adding a missing manual line only when a valid active generation exists.
- Save through the stable SCKRL-310 `saveReceiptReview` RPC/client with `generationId`,
  `expectedReviewRevision` and every current line. Update the UI from the returned server summary.
- Handle loading, retry, no active generation, empty parse/no items, load failure, save failure and
  stale 409-like conflicts without losing the user's visible draft.
- Separate review readiness from placement availability. A functional primary action should save
  the review. The placement CTA must remain disabled with clear copy such as "Placement is not
  available yet" until SCKRL-305/SCKRL-311 activates the handoff. Do not create a fake placement
  route, placeholder stock rows or direct stock writes.
- If all lines are ignored or excluded, the review can be saved, but placement eligibility remains
  false with explicit "No items to place" copy. Future SCKRL-305 owns activating navigation and
  atomic placement.

- create a fake placement route, placeholder stock rows or direct stock writes;
- implement SCKRL-407 or SCKRL-408;
- claim SCKRL-304 Done, Stage 1 exit, real-receipt acceptance, connected Supabase acceptance or
  native/device acceptance.

source review and Chair integration review pass. It does not become blocked on SCKRL-305/311; those
tickets own placement activation. The remaining SCKRL-304 gates are connected/runtime evidence after
the relevant migrations are available, and visual/accessibility review of the implemented screen.
