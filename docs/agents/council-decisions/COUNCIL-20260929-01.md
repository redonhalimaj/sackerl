## v1 recommendation

Add a Scan action labelled **Load sample receipt** and show it only when both `__DEV__` and
`EXPO_PUBLIC_APP_ENV === 'dev'` are true. Check the same condition in its handler. Explain before
creation that it saves sample data to the signed-in development household and is not a real
purchase. Use the existing auth context and household lookup, then `createReceipt` followed by
`promoteReceiptParse`. Use fixed, clearly synthetic grocery rows with valid categories, units,
confidence values and matching confidence levels. Mark the store
`Sackerl QA sample (not a real purchase)`, provider `development-fixture`, and the synthetic URI
uniquely per attempt. The promoted parser rows remain unresolved for explicit user review.

Use the existing Scan in-flight and request/session/focus guards for both normal capture and sample
creation. Reject stale work after each await and avoid two simultaneous actions. Persist the
per-attempt synthetic URI and any returned receipt ID through retry within the Scan session:

1. If a receipt ID is known, read `getReceiptReview` first. An active generation means promotion
   succeeded; open that review instead of promoting again. If no generation exists, promote with
   the receipt's expected generation and review revision.
2. If `createReceipt` might have committed but returned no ID, search the signed-in household's
   paginated `listReceipts` results for the exact synthetic URI before another create attempt. Keep
   the same URI while resolving the attempt. If recovery cannot complete or completes with no
   match, show an uncertain-outcome error and retain the attempt; do not automatically create
   again. Because this API has no idempotency key, even a completed no-match read cannot rule out a
   late first commit. A later explicit new sample attempt can leave an orphan development fixture.
3. A promotion conflict or unexpected existing generation requires a fresh review read. Do not
   overwrite an edited generation or invent a successful save.

Navigate to the existing `/receipt-review/[id]` route only for an authenticated, current Scan
request. The review screen's real RPC read/save remains the validation surface. No stock rows,
media files, OCR job, new schema, auth/RLS policy, or production parse claim is part of this work.
The development environment label is a client build gate, not proof of the backend's identity.

## Evidence and alternatives

- The owner-supplied simulator screenshot and
  [finding](../../product/simulator-findings-2026-09-29.md) show the no-generation fallback after
  simulated Scan, leaving the editor inaccessible through that path.
- [`createReceipt`](../../../packages/api-client/src/receipts.ts) has no client idempotency key.
  A lost response can leave a committed receipt; exact URI recovery is needed for a retry.
- `promoteReceiptParse` accepts authenticated calls and requires an expected active generation and
  review revision. The SCKRL-310 command is atomic, rejects stale updates and leaves parser rows
  unresolved. The target database must have that migration; its hosted state is not established by
  the local contract.
- Manual SQL or a preexisting isolated fixture could expose the editor but would not give the
  owner a repeatable path in the current Scan UI. Full real acquisition/OCR depends on SCKRL-307
  through SCKRL-309 and is outside this QA aid.

The strongest counterargument is that a development button writes synthetic data into a persistent
household and could be mistaken for a real receipt. The double build/environment gate, explicit
user action and copy, sample store/provider/URI markers, and no stock write contain that risk. The
record does not treat a sample promotion as evidence that real acquisition or OCR works.

## Final source acceptance of v1

The final implementation adds the gated action in `apps/mobile/app/(tabs)/scan.tsx`, the fixed
fixture and recovery flow in `apps/mobile/lib/sample-receipt.ts`, and focused Scan tests in
`apps/mobile/lib/scan-review-entry.test.tsx`. The code map was refreshed. The helper retains the
per-attempt URI and known receipt ID, reconciles an uncertain create through household-scoped
pagination without another insert, and reads the current review before promotion. If a promotion
response is lost, a subsequent read uses an already active generation and preserves any review
edits. Scan shares its in-flight and focus/session request guards across ordinary capture and the
sample action. No stock, media, OCR, migration, auth or RLS changes were made.

Independent QA inspected the final source and reported no blocking findings in
[the QA review](../../qa/sckrl-304-sample-review.md). QA reran 16 focused Scan tests, mobile
typecheck, mobile lint and `git diff --check`; all passed. The Chair reported an iOS export of
1,287 modules. The Deputy independently inspected the final Scan/helper/test diff and QA report,
and found the implementation consistent with v1. The actual underlying model identity of both
configured fallback agents remains unexposed.
